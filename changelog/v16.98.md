# v16.98-shared — no more 500s when the database is overloaded (Search Console "Server error (5xx)")

Eric (10 Nov): Google Search Console emailed "New reason preventing your pages from being indexed: Server error (5xx)".

## What happened
- Miami, 6, 7 and 8 Nov, once a day around 16:00–16:40 UTC: a scraper sent ~4,700 page requests in one minute from
  thousands of different addresses (about 10 each, ordinary Chrome browser, mostly Latin America and Spain). Miami's D1
  answered "D1 DB is overloaded. Too many resources consumed within a 10 second window", and ~1,000 requests a day
  got a 500 (Cloudflare: 1,380 / 1,108 / 966 exceptions). Smaller bursts (1–2k a minute, 4–5 Nov) were fine.
  Googlebot crawling in those minutes saw the 500s.
- Orlando had no errors. Tampa returns 503 on every page on purpose (maintenance page, docs/MAINTENANCE.md); if the
  Search Console email was for Tampa, that is the reason and it is expected.
- A per-visitor limit can't stop this scraper (each address sent ~10 requests).

## Changes (worker)
- Every good public page is also kept in the edge cache as a spare copy for 7 days (`staleKey`, `STALE_TTL`).
- If building a page fails (an error is thrown, or a 5xx comes back), the spare copy is served (`x-gl-cache: STALE`).
  With no spare copy, a short "We're a little busy right now" page with **503 + Retry-After: 60** and noindex,
  never a 500. Search engines treat 503 as "come back later" and keep the page.
- The home-page "Database not set up yet" 500 only shows for a real missing table; an overloaded database now goes
  through the spare-copy / 503 path above.
- Local tests only: header `x-gl-test-fail` with BV_TEST_ECHO simulates an overloaded database.
