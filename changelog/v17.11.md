# v17.11-shared — duplicate merge: several runs at once, and safer on a busy GHL

Eric (19 Nov): Miami must finish fast; "yes, v17.11". GHL answers slowly in the day (about 10 s per pair, one pair at a
time = ~340 merges an hour), so several runs at once are allowed.

## Change (worker)
- `/admin/merge` takes `part` and `of` (e.g. `POST /admin/merge?n=10&part=2&of=4`). The queue is split into `of` groups by
  the kept listing's id, so runs in different groups never touch the same business (all copies of one business share the
  same kept listing). Without the two options nothing changes (the 5-minute background job is unaffected).
- `ghlJson` waits and retries when GHL answers 429 (too many requests), up to 3 times.
- `mergePair` reads both contacts with `mergeGetContact`: only a real "not found" (400/404) means "gone". Before, any
  failed read (for example a 429) looked like "gone" and removed the pair from the list. A busy GHL now leaves the pair
  in the queue (no "failed" mark, nothing changed yet) and the next batch retries it.
- The delete step counts GHL's 400 "Contact not found" as already deleted (like 404). That was behind the two false
  "delete 400" failures of 19 Nov (two overlapping batches; both merges had in fact finished — checked in GHL).

## Rules for running several at once
- Never run two runs with the same `part`/`of`; use one run per `part` (0 … of-1), same `of` for all.
- Held-back pairs (claimed listing / owner record) stay in merge_log as 'skip' and are never picked up.
